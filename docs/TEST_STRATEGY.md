# Test Strategy

## 1. Test layers

### Unit tests

Run fast host tests without SDL windows for portable logic:

- Glass-safe rectangles, 30 px radius mask, status/subtitle non-overlap.
- Layout selection across Idle, Listening, Thinking, Speaking, Menu, Error.
- User STT retention across TTS and state transitions; replacement only by valid next STT.
- New TTS turn clears assistant text only.
- UTF-8-safe truncation, mixed text, empty text, and configured byte limits.
- Event schema validation, unknown version/type, duplicate/out-of-order times, and size limits.
- Virtual key short/long/press-release routing.
- Mock settings/profile transaction outcomes and reset semantics.

### Scenario tests

Run a fixture through the scenario engine with a virtual clock. Assert event order, state timeline, caption contents, page number, button action, and recovery result. Scenarios must be deterministic and must not wait for wall-clock delays.

Required starter scenarios:

1. Normal PTT → STT → Thinking → two TTS sentences → Idle.
2. User STT persists through every assistant sentence and is replaced by next valid STT.
3. Empty/invalid STT does not erase a valid user utterance.
4. Long Chinese/Latin mixed answer, pagination, and UTF-8 truncation.
5. OK interruption while Speaking, followed by a new listening turn.
6. Disconnect and reconnect timeout during Thinking/Speaking.
7. UDP sequence gap, out-of-order packet, and audio queue-full mock event.
8. Missing battery gauge and low-battery alert overlapping neither captions nor status.
9. Menu open/close and profile/config changes while caption pages are active.
10. Virtual dim/soft-sleep/deep-sleep deadlines and wake-key event sequence (logic only).

### Screenshot regression

- Capture only the 240×320 viewport, excluding desktop chrome/window bezel.
- Pin LVGL, fonts, SDL backend, color depth, and test OS image to limit nondeterminism.
- Store a small set of reviewed golden PNGs per important state.
- On mismatch, publish actual image, expected image, and a diff image as CI artifacts.
- Golden updates require reviewing the image diff and tying the change to an intentional UI behavior.
- Add geometry assertions for mask and text bounds so pixel comparisons are not the only oracle.

### Firmware build and real-device validation

- Any code shared with firmware must pass the relevant Passport build and size gate from the firmware repository.
- Desktop pass does not waive flashing a development Passport for LCD colors/contrast, font readability, physical controls, codec/audio, network path, battery and power tests.
- Record firmware SHA, simulator SHA, device model, scenario, network path, logs, and what was not tested.

## 2. Suggested commands after the host build exists

These commands are planned, not currently executable:

```sh
cmake -S . -B build -G Ninja -DCMAKE_BUILD_TYPE=Debug
cmake --build build --parallel
ctest --test-dir build --output-on-failure
./build/passport-simulator --scenario tests/scenarios/stt-retained-through-tts.json --screenshot out/stt-retained.png
```

Document the actual supported commands when P0-01 lands. Do not advertise commands as working before verifying them on a clean checkout.

## 3. CI gates

Initial CI should run on pull requests and pushes to the default branch:

1. Configure/build host targets on Ubuntu.
2. Run unit and scenario tests.
3. Run headless screenshot regression tests.
4. Upload screenshot diffs on failure.
5. Check formatting and fixture JSON validation.

macOS should be tested by documented local steps initially; add macOS CI when SDL/LVGL dependency setup is repeatable. Firmware CI remains the authority for firmware compilation and size.

## 4. Evidence labels

Every report or UI value must identify one of:

- **Simulated:** generated by a fixture or mock; useful for logic checks only.
- **Host-tested:** executed in the desktop test harness.
- **Firmware-built:** compiled for ESP32-C3; not proof of device behavior.
- **Device-tested:** exercised on physical AI Passport with recorded source/artifact identity.

Do not mix these labels or infer device stability from desktop screenshots.
